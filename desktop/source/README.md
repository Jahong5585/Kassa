# Касса минимаркета · Windows · 0.5.9

Для клиента 0.5.9 нужен API с многоролевой авторизацией и заголовком `X-Active-Role`.

Настольное рабочее место кассира для учебных продаж. Интерфейс повторяет структуру предоставленного макета. Пакет Windows x64 включает KassaSetup.exe, переносную сборку, исходники, START.txt и PILOT.md. Пилотный установщик поставляется без подписи издателя.

## Состав выпуска

- Локальная учебная смена, стартовый размен, закрытие по факту и расхождение.
- Учебный каталог из 12 товаров. Поиск по имени, ввод штрихкода и сканер в режиме клавиатуры с Enter. Выбор партии, ручной ввод веса, контроль остатка и суммы.
- Поиск подключённых USB-принтеров, официальный каталог драйверов и установка проверенного пакета. См. PRINTER_DRIVERS.md.
- До восьми быстрых кнопок для штучных товаров, в том числе без штрихкода. Закрепление из результатов поиска и добавление одной штуки по нажатию. Кнопки «−» и «+» в чеке меняют количество штучной позиции.
- Наличная оплата, расчёт сдачи, история и повторная печать нефискального документа через системное окно печати.
- Перед открытием окна наличной оплаты на стенде касса сверяет доступность API и открытой смены. Если проверка не проходит, диалог оплаты остаётся закрытым, а корзина сохраняется.
- В режиме стенда можно сохранить отложенный чек, сверить цены и остатки при восстановлении и провести продажу с привязкой к этому чеку. При изменении состава сохранённый чек можно отменить с причиной и собрать заново.
- Поиск по полному ID чека, частичные и полные наличные возвраты, проверка остатка количества, карантин или возврат на остаток, печатная форма возврата.
- Сверхлимитный возврат сохраняет запрос с исходным ID. В учебном режиме лимит составляет 20 000 сум суммарно на чек. На стенде действует серверный лимит, а решение принимает администратор через отдельное окно. С настроенным профилем администратор входит в отдельном сеансе через браузер с политикой MFA стенда.
- Внесения и изъятия с указанием причины, журнал смены и проверка доступных наличных.
- Сроки годности, включая просроченные партии и обязательную отсутствующую дату. Отметка о снятии создаёт задачу администратору.
- Рабочее место приёмщика. Поставщик, ожидаемый заказ, штрихкод, количество, отдельные партии и сроки. Неизвестный штрихкод можно отправить как предложение карточки. Администратор может опубликовать карточку или отклонить предложение с комментарием.
- Накладные. Черновик, передача на проверку, возврат с причиной, отмена и проведение. Проверка вложений выполняется на сервере. В локальном режиме используется учебная отметка вместо файла. Фактические файлы передаются через отдельное окно Windows в режиме стенда, оригинал скачивает администратор.
- Закупочная стоимость заполняется администратором для каждой партии. Остатки меняются после проведения накладной. Склад включает карантин, списания, обработку задач по снятию с полки и инвентаризацию выбранной партии.
- Для приёмки и склада используется отдельный сеанс магазина. Учебные данные общие для ролей и кассы. Внешний стенд проверяет роль и доступ к магазину. Клиент использует серверную версию документа и сохраняет запрос при неясном исходе.
- В верхней панели доступно переключение только между ролями, назначенными текущему пользователю. Роль владельца раскрывает режимы кассира, приёмщика и администратора, но не обходит серверные проверки магазина, кассы и MFA.
- В настройках по умолчанию включена защита данных магазина. Она блокирует изменение каталога, цен, накладных и складских данных до явного отключения с подтверждением, не мешая обычной продаже кассира.
- Режим отдельного HTTPS-стенда. Операции клиента сверены с KASA_API.md и ответами из исходного кода сервера Jahong5585/Kassa, main, коммит 43129ab13f3328da9dade49cd2725b7b056d8b77.
- Перед отправкой изменяющей операции клиент записывает её в локальный журнал. При неясном исходе продажи и возврата клиент проверяет тот же ID. Внесение или изъятие сверяется по журналу смены. Если подтверждение не найдено, клиент повторяет исходное тело. Для отметки о снятии с полки применяется идемпотентный повтор с тем же ID, поскольку API кассира не предоставляет чтение такой задачи по ID. В режиме стенда журнал зашифрован Windows DPAPI и разделён по серверу, кассе и субъекту токена. Ключ и токен находятся в памяти процесса.
- Интерфейс доступен на русском и узбекском (латиница). Время операций отображается в Asia/Tashkent.

## Управление магазином

Откройте «Приёмка → Администратор → Управление».

- **Каталог.** Поиск, редактирование карточки, несколько штрихкодов и упаковки, изменение цены и история. CSV сначала проходит предпросмотр. Для нового товара укажите expectedVersion = 0. Если сразу задана цена, expectedPriceVersion = 1. Заголовок шаблона показан в форме импорта. Предел одного файла на стенде — 48 000 символов. Введите или вставьте содержимое UTF-8 CSV.
- **Поставщики.** Карточка поставщика, срок поставки, закупочные цены и версии упаковки. Для привязки закупочной цены нужен полный ID товара из каталога.
- **Закупки.** Ручной заказ или расчёт по предложению поставщика. Отмечаются недостаток истории и ручной спрос. Расчёт на стенде выполняет API. Сохранение или пересчёт заказа создаёт черновик новой версии. Перед отметкой отправки его утверждают. Отметка регистрирует факт отправки по указанному подтверждению. После неё заказ доступен приёмщику.
- **Отчёты и аудит.** Продажи, оплаты, возвраты, выручка и маржа, движения, потери, журнал действий. Укажите период. Четыре отчёта выгружаются в CSV. В учебном режиме расчёты используют локальные операции, маржа по продажам с отсутствующей себестоимостью выводится как недоступная.
- **Стенд.** Профиль KasaPilot.json задаёт адрес API, магазин и параметры входа. В браузерных проверках использовались локальные данные и имитация моста API. Проверка на Windows и авторизованном стенде остаётся частью пилота.

## Сборка на Windows

Требуется SDK .NET 8 или новее. В PowerShell из папки исходников выполните:

    dotnet build .\KasaDesktop.csproj -c Release

Запуск из bin\Release\net48\KasaDesktop.exe. Для рабочего окна требуются .NET Framework 4.8+ и Microsoft Edge WebView2 Runtime. Упаковывайте весь выходной каталог, включая папку web и нативный загрузчик WebView2 x64.

## Проверка

Из корня исходников установите Playwright и выполните браузерный сценарий:

    npm install --no-save playwright
    npx playwright install chromium
    node tests/browser.mjs

Сценарий проверяет учёт наличных, известный и неизвестный штрихкод, партии, вес, восстановление корзины, проверку потери ответа, историю, чек, пересчёт смены, малые окна и восстановление ожидающей API-операции после перезапуска на имитации настольного моста. Также проверяются частичный и полный возвраты, сверхлимитный возврат после перезапуска, внесение, изъятие, отказ сверх остатка, фильтры сроков, сохранение остатка после снятия с полки и имитация потери ответа для трёх новых операций. Проверяются черновик на 12 штук в двух партиях, передача файла, возврат на правку, стоимость, однократное увеличение остатков при потере ответа и повторе, ограничение роли, карантин и инвентаризация. Для записи контрольных изображений и печатного PDF задайте KASA_QA_DIR.

Сценарий также проверяет переключение языка, продажу и отчёт на узбекском, клавиатурный ввод веса и серию из 30 сканирований при задержке записи. Тест OIDC с локальным имитатором запускается командой `dotnet run --project tests/auth/AuthTests.csproj`.

Реальный Windows-запуск, авторизованный сервер, драйвер принтера, сканер, весы и файлы накладной требуют проверки на пилотном ПК. В PILOT.md приведены настройка OIDC, протокол приёмки и процедура подписи.

## План выпусков

| Этап | Объём |
| --- | --- |
| 1 | Смена, каталог кассира, наличная продажа, нефискальный чек, журнал и сверка потерянного ответа |
| 2 | Возвраты, подтверждение исключений администратором, кассовые внесения и изъятия, сроки годности |
| 3 | Рабочее место приёмщика, черновик и вложение накладной, проверка и проведение, склад |
| 4 | Каталог администратора, закупки, отчёты, настройки и журнал действий |
| 5 | Персональный вход, узбекская локализация, диагностика устройств и пилотный установщик |

Банковские и фискальные операции относятся к отдельному согласованию по ТЗ.
