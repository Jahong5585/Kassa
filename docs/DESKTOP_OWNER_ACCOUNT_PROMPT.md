# Промт для разработчика Windows-программы «Касса»

Работай с актуальным исходным кодом Windows-программы «Касса» в отдельной ветке. Не удаляй и не ослабляй существующие OIDC, MFA, FIDO2/USB и разграничение ролей. Базовый рабочий API: `https://kassa.qr-space.uz`. Получай точный контракт текущего сервера из защищённого `GET /openapi/v1.json`; краткое описание находится в `docs/KASA_API.md` серверного репозитория.

## Цель

В разделе «Платформа» сделай штатный интерфейс, через который разработчик платформы с `canWrite=true` создаёт тестовый магазин, создаёт для него реальную учётную запись владельца и получает временный пароль один раз. После этого владелец должен входить в Windows-программу через обычный OIDC и при первом входе сменить пароль и настроить TOTP. Пользователь не должен вводить OIDC `subject` вручную и не должен каждый раз обращаться к администратору сервера.

## Серверный контракт

Все маршруты требуют `Authorization: Bearer <access_token>`.

1. `GET /v1/platform/me` — проверить `canRead` и `canWrite`.
2. `GET /v1/platform/stores?offset=0` — получить тестовые магазины. Элемент содержит `organizationId`, `organizationName`, `storeId`, `storeName`, `timeZone`, `version`, `isTest`, `ownerSubject` (`null`, если владельца ещё нет).
3. `POST /v1/platform/stores` — создать тестовый магазин. Передавай сгенерированные UUID, названия, `timeZone: "Asia/Tashkent"`, `ownerSubject: null` и понятную `reason`. Не показывай поле `ownerSubject` пользователю.
4. `PUT /v1/platform/organizations/{organizationId}/stores/{storeId}/name` — переименовать; передать `expectedVersion`, `name`, `reason`.
5. `POST /v1/platform/organizations/{organizationId}/stores/{storeId}/owner-account` — создать или заменить владельца.

Тело пункта 5:

```json
{
  "username": "owner.login",
  "firstName": "Имя",
  "lastName": "Фамилия",
  "email": null,
  "replaceSubject": null,
  "reason": "Создание владельца тестового магазина"
}
```

Для магазина без владельца передавай `replaceSubject: null`. Если `ownerSubject` уже заполнен, покажи действие «Заменить владельца» и передай это точное значение как `replaceSubject`. Это оптимистическая защита от параллельного изменения.

Успешный ответ:

```json
{
  "organizationId": "uuid",
  "storeId": "uuid",
  "subject": "oidc-subject",
  "username": "owner.login",
  "temporaryPassword": "показывается только в фактическом ответе",
  "passwordTemporary": true,
  "requiredActions": ["UPDATE_PASSWORD", "CONFIGURE_TOTP"]
}
```

## Интерфейс

- В мастере создания магазина сначала создай магазин без владельца, затем открой шаг «Учётная запись владельца». Если второй шаг не удался, магазин остаётся видимым со статусом «Владелец не назначен» и действие можно безопасно повторить.
- В строке существующего магазина показывай «Создать владельца», если `ownerSubject == null`, иначе «Заменить владельца».
- Диалог спрашивает логин, имя, фамилию, email и причину. Логин обязателен: 3–64 символа, латинские буквы, цифры, `.`, `_`, `-`. Причина обязательна. Поля `subject`, Client Secret и служебные настройки пользователю не показывать.
- После успеха покажи отдельное окно: логин, временный пароль, кнопки «Копировать логин» и «Копировать пароль», предупреждение «Пароль показывается один раз. При первом входе его нужно сменить и подключить приложение-аутентификатор».
- После закрытия окна очисти временный пароль из памяти состояния. Не сохраняй его в настройках, локальной БД, логах, аналитике, crash report, истории запросов или буфере дольше явного действия пользователя.
- Обнови список магазинов после успеха. Не пытайся использовать возвращённый `subject` как пароль или логин.

## Ошибки

- `400` — подсветить ошибочные поля; учитывать `code`.
- `401` — повторный OIDC-вход.
- `403` — нет глобального права изменения или не выполнена рабочая аппаратная защита.
- `404 test_store_not_found` — обновить список.
- `409 identity_username_conflict` — предложить другой логин.
- `409 platform_owner_already_assigned`/`platform_owner_changed` — обновить магазин и попросить подтвердить замену заново.
- `429` — не повторять автоматически сразу, показать ограничение частоты.
- `503 identity_provisioning_disabled`/`identity_provisioning_unavailable` — сообщить, что сервис создания учётных записей временно недоступен; магазин не удалять.

## Обязательные проверки

Добавь модульные и UI-тесты: создание магазина без технического subject; создание владельца; замена существующего владельца; конфликт логина; отсутствие `canWrite`; 429/503; очистка пароля после закрытия; отсутствие пароля в логах и постоянном хранилище. Собери Windows-установщик в отдельной ветке, проверь вход нового владельца через обычный OIDC, смену временного пароля и обязательную настройку TOTP. В отчёте укажи ветку, версию EXE, SHA-256 и фактически пройденные тесты. Пароли, токены и ключи в отчёт не помещай.
