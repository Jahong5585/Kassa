# Серверный выпуск для Desktop 0.8.28

## Подтверждённая причина предупреждения

Production обслуживал API из коммита `35321fe`. Reverse proxy передавал исходный путь без изменения, но в этой
сборке ещё не были зарегистрированы расходы, сводный финансовый отчёт и предварительная загрузка каталога.
Поэтому фоновые запросы Desktop доходили до ASP.NET Core и завершались `404 application/problem+json`:

- `GET /v1/stores/{storeId}/finance/expenses?...`;
- `GET /v1/reports/stores/{storeId}/finance?...`;
- `GET /v1/catalog/snapshot`.

В тех же сеансах API возвращал `200` для товаров (включая вторую страницу), партий, накладных и их подробностей,
поставщиков, заказов, инвентаризаций, задач снятия с полки и отчёта прибыли. Это исключило ошибку маршрутизации
reverse proxy и отсутствие доступа к магазину как причину исходного предупреждения.

## Контракт синхронизации

### Полная загрузка каталога

`GET /v1/catalog/snapshot?after={productId}`

Обязательные заголовки: `Authorization`, `X-Operator-Session`, `X-Active-Role: cashier`, `X-Register-Id` и один из
действующих заголовков кассового устройства. Страница содержит не более 50 товаров, `nextAfter` и
`changeCursor`. Клиент сохраняет `changeCursor` первой страницы, загружает все страницы по `nextAfter`, затем
запрашивает изменения после сохранённого курсора.

### Последующие изменения

`GET /v1/catalog/changes?cursor={changeCursor}&limit=50`

Ответ содержит:

- `items` — актуальные карточки, штрихкоды, цены и доступные партии;
- `removedProductIds` — архивированные, удалённые или оставшиеся без действующей цены товары;
- `cursor` — последний обработанный устойчивый курсор;
- `nextCursor` и `hasMore` — продолжение страницы.

Курсор хранится в PostgreSQL и не зависит от перезапуска API. Изменения товаров, штрихкодов, цен, партий,
уценок и количественных акций регистрируются транзакционными триггерами. `410 catalog_cursor_invalid` означает,
что клиент должен повторить полную загрузку. Неизвестный магазин и отсутствие прав не подменяются пустым ответом.

### Автозаполнение закупочной цены

- `GET /v1/stores/{storeId}/procurement/suppliers/{code}/products/{productId}/price-template`;
- `GET /v1/stores/{storeId}/procurement/suppliers/{code}/price-options?productId={productId}&offset=0`.

Оба маршрута доступны активным ролям `receiver` и `admin` в выбранном магазине. Срок хранения товара передаётся
полем `shelfLifeDays`, а срок действия закупочной цены — отдельными `validFrom` и `validThrough`.

## Сохранённая совместимость

- OIDC + PKCE Desktop и мобильная авторизация не изменены;
- `Auth:RequireOperatorSession` сохраняет действующее значение;
- старые маршруты, `X-Register-Key`, `X-Register-Device-Token` и существующие привязки сохранены;
- проведение продажи остаётся атомарным; `operationId` обеспечивает безопасный повтор после потери ответа;
- локальная очередь и незавершённая корзина остаются ответственностью Desktop, сервер принимает повтор операции
  без повторного списания.

## Миграции

- `042_operating_expenses.sql` — операционные расходы;
- `043_catalog_change_feed.sql` — устойчивая лента изменений каталога.

Откат API выполняется возвратом сохранённого предыдущего образа. Таблицы 042 и 043 можно оставить: старая сборка
их не использует. SQL-откат 042 удаляет расходы и допустим только после отдельной копии; SQL-откат 043 удаляет
только ленту и триггеры, после чего клиенту потребуется новая полная загрузка.
