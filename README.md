# Касса Минимаркет

Бэкенд на ASP.NET Core 10 и PostgreSQL для кассира, приёмщика и админа. Поддерживаются учебные продажи и возвраты наличными и ручным безналом, кассовые смены, приёмка напрямую по накладной и по заказу, поставщики, файлы накладных, закупочная стоимость прихода, сроки годности, складские операции, каталог, розничные цены, кассовые операции, согласование закупок, возвраты поставщикам, взаиморасчёты и рекомендации по пополнению. В стендовой модели один склад соответствует одной торговой точке.

## Запуск и проверка

Потребуются .NET 10 SDK, Docker с Compose, Python 3, Bash и curl. Из корня проекта выполните:

```sh
bash tests/run.sh
```

Команда создаёт изолированную временную базу с учебными данными, запускает API на loopback и проверяет кассу, возвраты, приёмку, поставщиков, файлы, стоимость, складские операции, каталог, переоценку, импорт, закупки, взаиморасчёты, расчёт пополнения, отчёты и права доступа. Для проверки трёх исходов антивируса сценарий запускает локальный имитатор протокола ClamAV. Тестовая база удаляется при завершении. Можно выбрать другие локальные порты через `POS_TEST_DB_PORT` и `POS_TEST_API_PORT`.

Для серверной приёмки с проверкой восстановления выполните `bash tests/run.sh --restore`. Сценарий подтверждает версию PostgreSQL 17, применяет миграции в изолированном проекте Compose, прогоняет API и аудит, затем восстанавливает учебный дамп в отдельную временную базу. Перед завершением сверяются контрольный чек, закрытая смена, выбытие партии, её остаток и запись аудита. Рабочие базы и тома в этом сценарии не используются.

`compose.yaml` также запускает постоянную локальную БД. Перед запуском задайте разные значения `POS_DB_OWNER_PASSWORD` и `POS_DB_APP_PASSWORD` в защищённых настройках среды. Начальная миграция и выдача минимальных прав выполняются владельцем при первом запуске пустого тома. В приложении задайте `ConnectionStrings__Pos` для пользователя `kasa_api`. Для существующей базы применяйте только отсутствующие миграции один раз в порядке номеров до запуска нового API. Перед `016_opening_stock.sql` сохраните резервную копию. ## Контракт API

| Метод и маршрут | Доступ и результат |
| --- | --- |
| `POST /v1/shifts` | Кассир. Принимает `shiftId` и `openingCash`. На кассе и у кассира может быть только одна открытая смена. |
| `GET /v1/shifts/{id}` | Кассир. Читает свою смену на зарегистрированной кассе. Ожидаемый остаток и оборот наличных видны после пересчёта. |
| `POST /v1/shifts/{id}/close` | Кассир. Принимает `countedCash` и возвращает ожидаемый остаток и расхождение. |
| `GET /v1/catalog/barcodes/{barcode}` | Кассир. Возвращает розничную цену, её версию и годные партии своей точки. |
| `POST /v1/sales` | Кассир. Фиксирует продажу, строки, способ оплаты и списания в одной транзакции. |
| `GET /v1/sales/{id}` | Кассир. Возвращает свою сохранённую продажу по исходному `operationId` для сверки или повторной печати. |
| `GET /v1/reports/stores/{storeId}/registers/{registerId}/shifts/{id}` | Админ назначенной точки. Наличный и безналичный оборот разделены. |

Документ OpenAPI доступен через `GET /openapi/v1.json` с Bearer-токеном. Для кассовых вызовов дополнительно передаются `X-Register-Id` и `X-Register-Key`. Организация и точка определяются сервером по действующей учётной записи и устройству.

Пример тела `POST /v1/sales` с учебными идентификаторами:

```json
{
  "operationId": "caf8837e-c82d-4606-a5c7-3b7fc1cbb1e6",
  "shiftId": "b296c6a6-6d0e-4066-83cc-e50412c1bf5b",
  "method": "manualCashless",
  "tendered": null,
  "items": [{
    "productId": "00000000-0000-0000-0000-000000000041",
    "lotId": "00000000-0000-0000-0000-000000000051",
    "priceVersion": 1,
    "quantity": 1
  }]
}
```

Ручной безнал записывает полную сумму продажи в безналичный оборот без обращения к платёжным системам. Для `cash` клиент указывает внесённую сумму в `tendered`. Итог и сдачу рассчитывает сервер. Каждый чек содержит признак «Тестовый • нефискальный».

Касса создаёт `operationId` перед первым запросом и сохраняет вместе с корзиной. При потере ответа выполняет `GET /v1/sales/{operationId}`. Если результат ещё не виден, касса может повторить первоначальное тело с тем же ID. Сервер возвращает сохранённый результат либо проводит продажу один раз. Повтор с изменённым телом возвращает `409`. При изменении цены сервер возвращает `price_changed`, при недоступной партии или нехватке товара — `lot_not_sellable_or_insufficient_stock`.

Для стенда сумма строки округляется до 0,01 сума, половина округляется от нуля. Для штучного товара допустимо целое количество, для весового — до трёх знаков. Продажа разрешена по дату годности включительно в часовом поясе точки. Кассир сверяет маркировку на упаковке и передаёт выбранный `lotId`. Правила округления и границу годности нужно утвердить перед пилотом.

## Возвраты

| Метод и маршрут | Доступ и результат |
| --- | --- |
| `GET /v1/sales/{sourceRegisterId}/{id}/refund-options` | Кассир. Позиции исходной продажи в своей точке, проданное и уже возвращённое количество и сумма. |
| `GET /v1/stores/{storeId}/sales/{sourceRegisterId}/{id}/refund-options` | Админ. Те же сведения для проверки в назначенной точке. |
| `POST /v1/refunds` | Кассир в открытой смене. Проводит полный или частичный возврат с уникальным `operationId`. |
| `GET /v1/refunds/{id}` | Кассир. Сохранённый результат своего возврата по `operationId`. |
| `POST /v1/stores/{storeId}/refund-approvals` | Админ. Подтверждает конкретный запрос, кассу и сумму. |

Тело возврата содержит `operationId`, `shiftId`, `sourceRegisterId`, `saleId`, `reason` и `items`. Каждая строка содержит `productId`, `lotId`, `quantity` и `destination` со значением `stock` или `quarantine`. Если партия уже просрочена, заблокирована или лишена обязательной даты, сервер помещает товар в карантин. Сумма рассчитывается из итоговой суммы исходной строки. При нескольких частичных возвратах разница округления остаётся учтённой в сумме полного возврата.

`Refunds__CashierLimit` задаёт суммарный лимит самостоятельных возвратов по одному исходному чеку. Значение по умолчанию 0 требует подтверждения админа для каждого возврата. При `refund_approval_required` передайте админу тот же запрос. Для подтверждения API принимает `registerId`, `amount` и исходный объект `refund`. После подтверждения касса повторяет своё тело с прежним `operationId`. Смена, исходный чек, позиции, сумма и причина подтверждаются как одно действие. В отчёте смены `cashRefunds` уменьшают ожидаемую наличность, `manualCashlessRefunds` показываются отдельно. Ручная безналичная операция фиксируется как учётная запись.

## Приёмка и заказы

Маршруты этого раздела имеют префикс `/v1/stores/{storeId}`. Приёмщик и админ получают доступ в своей точке. Приёмщик редактирует и отправляет на проверку свои черновики. Админ может вернуть их с причиной и провести проверенную версию.

| Метод и маршрут | Действие |
| --- | --- |
| `GET /receiving/catalog/barcodes/{barcode}` | Найти товар и базовую единицу без финансовых полей. |
| `GET /purchase-orders`, `GET /purchase-orders/{id}` | Список ожидаемых заказов и их остатки. Чтобы включить завершённые, передайте `openOnly=false`. |
| `POST /purchase-orders` | Админ регистрирует ожидаемую поставку. Поля `orderId`, `supplierRef`, `items` со строками `productId` и `quantity`. |
| `POST /receipts` | Создать черновик по номеру и дате накладной. |
| `GET /receipts`, `GET /receipts/{id}` | Список и карточка. Для списка доступны `status` и `offset`. |
| `PUT /receipts/{id}` | Заменить строки черновика. Поля `expectedVersion` и `items`. |
| `POST /receipts/{id}/submit` | Передать указанную версию на проверку. |
| `POST /receipts/{id}/return-to-draft` | Админ возвращает на правку. Поля `expectedVersion` и `reason`. |
| `POST /receipts/{id}/post` | Админ проводит версию из `expectedVersion`. |
| `POST /receipts/{id}/cancel` | Приёмщик отменяет свой черновик. Админ может отменить черновик или документ на проверке. Передайте `expectedVersion` и `reason`. |

Отмена переводит документ в конечный статус `cancelled`. Автор, время, причина и вложения сохраняются, остатки и исполнение заказа не меняются. Точный повтор от того же сотрудника возвращает сохранённую карточку. Для просмотра списка передайте `status=cancelled`. После отмены те же реквизиты накладной можно зарегистрировать с новым `receiptId`, при этом действующие и проведённые накладные сохраняют защиту от дублей.

При создании черновика передаются `receiptId`, `supplierRef`, `invoiceNumber`, `invoiceDate`, необязательный `purchaseOrderId` и строки `items`. Строка содержит `productId`, `lotId`, `expiryDate` и `quantity` в базовой единице. Реквизиты накладной остаются постоянными после создания. Срок нужен для продуктов с соответствующим признаком, просрочка блокирует проведение. Повтор проведения той же версии возвращает сохранённый результат. При проведении остатки, движения и исполнение заказа сохраняются вместе. Для привязанного заказа сервер блокирует избыточную поставку. `supplierRef` хранит ссылку на поставщика в текстовом виде.

## Поставщики

Маршруты имеют префикс `/v1/stores/{storeId}`.

| Метод и маршрут | Действие |
| --- | --- |
| `GET /suppliers` | Приёмщик и админ видят код и название активных поставщиков. Админ может включить отключённых через `activeOnly=false`. |
| `GET /suppliers/{code}` | Админ читает карточку с ИНН, контактами, условиями оплаты, сроком поставки и версией. |
| `PUT /suppliers/{code}` | Админ создаёт карточку с `expectedVersion: 0` или обновляет её по текущей версии. Поля `name`, `active`, `taxId`, `phone`, `email`, `paymentTerms`, `leadTimeDays`. |

Код состоит из 1–32 латинских букв, цифр, дефисов и подчёркиваний и начинается с буквы или цифры. Для новых заказов и прямых приходов используйте код карточки в `supplierRef`. Отключение запрещает новые заказы и прямые приходы по коду. Ранее созданные заказы можно исполнить. Для совместимости текстовые ссылки на поставщиков по умолчанию допустимы. `Purchasing__RequireSupplierCard=true` требует карточку для новых заказов и прямых приходов.

## Закупки и взаиморасчёты

Маршруты с префиксом `/v1/stores/{storeId}/procurement` доступны админу назначенной точки.

| Метод и маршрут | Действие |
| --- | --- |
| `GET /suppliers/{code}/prices` | Действующий прайс на дату точки. Можно передать `asOf` и `offset`. |
| `GET /suppliers/{code}/prices/{sku}` | История версий цены по артикулу поставщика. |
| `PUT /suppliers/{code}/prices/{sku}` | Новая версия. Поля `expectedVersion`, `productId`, `packageUnit`, `unitsPerPackage`, `packagePrice`, `validFrom`, необязательное `validThrough`. |
| `GET /orders`, `GET /orders/{id}` | Список и карточка заказа с закупочными ценами. Для списка доступны `stage` и `offset`. |
| `PUT /orders/{id}` | Сохранить черновик. Поля `expectedRevision`, `supplierCode`, `expectedDeliveryDate` и `items` с `supplierSku`, `priceVersion` и целым числом упаковок `packages`. |
| `POST /orders/{id}/approve` | Утвердить указанную `expectedRevision`. |
| `POST /orders/{id}/mark-sent` | Отметить отправку утверждённой `expectedRevision` и сохранить `reference`, например номер письма. |
| `POST /returns`, `GET /returns/{id}` | Провести возврат поставщику и прочитать результат по `returnId`. |
| `POST /suppliers/{code}/payments`, `GET /suppliers/{code}/payments` | Записать факт оплаты и получить журнал. Поля `operationId`, `amount`, `paymentDate` и `reference`. |
| `GET /suppliers/{code}/balance` | Стоимость проведённых приходов, стоимость возвратов, сумма оплат и остаток. |

У первой записи прайса `expectedVersion: 0`. Даты действия включительны. Из подходящих записей приоритет у самой поздней даты начала, затем у большей версии. Для нового заказа передайте `expectedRevision: 0`. Сервер фиксирует состав, упаковку и цену для каждой версии. При изменении утверждённого заказа статус возвращается в черновик. При утверждении сервер сверяет версии с действующим прайсом и возвращает `409 supplier_price_changed`, если цена успела измениться.

Отметка отправки записывает действие администратора. После неё приёмщик видит товар, базовое количество, ожидаемую дату и остаток к поставке через `/purchase-orders/{id}`. Частичные поставки проводятся отдельными накладными. Для повторения команды после тайм-аута сохраните исходный ID и тело запроса. При конфликте версии загрузите актуальную карточку перед повторным изменением.

Возврат принимает `returnId`, `receiptId`, `reason` и строки `items` с `productId`, `lotId`, `quantity` и `bucket` (`stock` или `quarantine`). Суммарное возвращённое количество по партии ограничено фактически принятым по исходной накладной. Остаток, движение и документ возврата сохраняются в одной транзакции. Возврат уменьшает складской остаток, а исполнение заказа остаётся в истории. При наличии стоимости прихода сумма возврата рассчитывается пропорционально исходной строке.

Взаиморасчёты учитывают проведённые накладные с кодом карточки поставщика. Остаток равен учтённой стоимости приходов за вычетом возвратов и вручную зарегистрированных оплат. Отрицательное значение соответствует превышению учтённых оплат и возвратов над приходом. Поля `unpricedReceipts` и `unpricedReturns` показывают количество документов, для которых суммы неизвестны. Повтор оплаты с тем же ID возвращает исходную запись. Повторная запись с другой операцией, но той же датой и номером у поставщика возвращает `409`.

### Сверка оплат по накладным

Префикс маршрутов — `/v1/stores/{storeId}/procurement/suppliers/{code}`. Доступ есть у админа назначенной точки.

| Метод и маршрут | Действие |
| --- | --- |
| `GET /invoices`, `GET /invoices/{id}` | Проведённые накладные, суммы, сроки и статус. Список поддерживает `offset`. |
| `PUT /invoices/{id}/due-date` | Сохранить срок оплаты `dueDate` с `expectedVersion`. Первая версия начинается с 0, явный `null` снимает срок. |
| `GET /invoices/{id}/allocations` | История распределений по накладной, включая отмены. |
| `GET /payments/{id}/allocation-balance` | Оплата и её распределённая и свободная суммы. |
| `POST /payment-allocations` | Распределить оплату по одной или нескольким накладным. Передайте `operationId`, `paymentId` и `items` с `receiptId` и `amount`. |
| `GET /payment-allocations/{id}` | Прочитать исходную операцию распределения. |
| `POST /payment-allocations/{id}/reverse` | Отменить распределение целиком новой операцией с `operationId` и `reason`. |

Регистрация оплаты и распределение выполняются отдельно. Свободная часть оплаты остаётся авансом и может быть распределена позже. Админ явно указывает накладные. Сервер проверяет поставщика, остаток платежа и долг по каждой накладной. Ошибка в любой строке отклоняет всё распределение. После тайм-аута повторите запрос с исходным ID и теми же данными. При изменении данных под тем же ID API возвращает `409`. Для исправления привязки отмените исходное распределение и отправьте новое. Сумма зарегистрированной оплаты при этом сохраняется.

Долг по накладной равен стоимости прихода за вычетом зачётов по возвратам, действующих распределений и полученной переплаты, плюс переданная переплата. Документы с неизвестной стоимостью показываются со статусом `unpriced`. Просрочка появляется после указанной даты оплаты по местному времени точки, если остался долг. При неизвестном сроке поле `dueDate` равно `null`.

Админ с MFA может сверить всех поставщиков точки через `GET /v1/reports/stores/{storeId}/supplier-settlements`. Передайте `supplierCode` для точного отбора и `nextOffset` как `offset` для следующей страницы. Отчёт показывает проведённые приходы, возвраты, зарегистрированные оплаты, нераспределённый аванс и отдельно сальдо, долг по открытым накладным и просроченный долг. При неизвестной части данных полный показатель равен `null`, а сумма известных значений и число строк без оценки доступны отдельно. Дата расчёта определяется часовым поясом магазина.

### Зачёт переплаты между накладными

Маршруты используют тот же префикс поставщика и требуют права админа точки.

| Метод и маршрут | Действие |
| --- | --- |
| `POST /credit-transfers` | Перенести переплату. Передайте `operationId`, `sourceReceiptId`, `targetReceiptId`, `amount` и `reason`. |
| `GET /credit-transfers/{id}` | Прочитать исходную операцию. |
| `GET /invoices/{id}/credit-transfers` | Входящие и исходящие зачёты по накладной, включая отмены. Список поддерживает `offset`. |
| `POST /credit-transfers/{id}/reverse` | Отменить зачёт отдельной операцией с новым `operationId` и `reason`. |

Зачёт возможен между двумя проведёнными накладными одного поставщика в одной точке. Сумма ограничена переплатой на исходной накладной и долгом на целевой. Поля `creditSentAmount` и `creditReceivedAmount` показывают суммы действующих зачётов. Платёжные записи и общий баланс поставщика учитываются отдельно от внутренних зачётов.

При потере ответа повторите исходный запрос. Тот же ID с другими параметрами даёт `409`. Если отмена зачёта или распределения оплаты лишит следующий зачёт его основания, сервер вернёт `409 supplier_credit_transfer_depends_on_settlement`. В истории накладной найдите последующий исходящий зачёт и отмените его первым. Все записи и их отмены сохраняются в аудите.

## Рекомендации по закупке

Маршруты с префиксом `/v1/stores/{storeId}/procurement` доступны админу назначенной точки.

| Метод и маршрут | Действие |
| --- | --- |
| `GET /replenishment-policies/{code}/{sku}` | Прочитать настройки пополнения для артикула поставщика в своей точке. |
| `PUT /replenishment-policies/{code}/{sku}` | Сохранить `settings` по `expectedVersion`. Для первой версии передайте 0. Повтор того же тела возвращает сохранённую версию. |
| `GET /recommendations/{code}/{sku}` | Рассчитать потребность по актуальным данным и сохранённой версии настроек. |
| `GET /recommendations/{code}/{sku}/snapshot` | Прочитать последний результат фонового расчёта и его статус. |
| `POST /recommendations/{code}/{sku}` | Разовый расчёт с параметрами из запроса. Тело `{}` использует значения по умолчанию. |
| `GET /products/{productId}/stockout-days/{day}` | Посмотреть отметку о подтверждённом отсутствии товара в дату `YYYY-MM-DD`. |
| `PUT /products/{productId}/stockout-days/{day}` | Зафиксировать или отозвать отметку за завершённый день. Передайте `expectedVersion` (0 для новой отметки), `confirmed` и `reason`. |

Сохранённый и разовый расчёты используют одинаковые параметры. По умолчанию `historyDays=28`, `minimumHistoryDays=7`, `coverageDays=5`, `safetyStock=0`, `minimumPackages=1`. Поле `leadTimeDays` переопределяет срок из карточки поставщика. `orderWeekdays` содержит номера дней от 1 (понедельник) до 7 (воскресенье), по умолчанию заказывать можно каждый день. `orderCutoffTime` задаёт время окончания приёма заказов в часовом поясе точки, например `15:30:00`. Начиная с этого времени выбирается следующий допустимый день. `manualDailyDemand` позволяет админу явно задать расчётный дневной темп.

Дневной спрос — среднее фактическое проданное количество по завершённым дням в часовом поясе точки. Дни до первой наблюдаемой продажи в окне и подтверждённые дни отсутствия исключаются из знаменателя. Ответ возвращает выборку и признак недостатка истории. При недостатке истории и отсутствии ручного темпа объём не предлагается. При прогнозе на остаток текущего дня из дневного темпа вычитаются уже проведённые сегодня продажи.

Расчёт использует согласованный снимок базы и показывает версию алгоритма, время, ближайшее и следующее окна доставки, приходящий остаток и даты риска. Партии расходуются начиная с ближайшего срока годности. Просрочка, карантин и партии без обязательной даты исключаются из доступного остатка. Количество, которое истечёт до прихода или в периоде покрытия, показано отдельно. Входящие поставки считаются пригодными с плановой даты до появления фактических партий. В размер заказа входят подтверждённые поставки до планового прихода включительно. Поздние поставки показываются отдельно и участвуют в прогнозе риска только с собственной даты. Просроченные и недатированные заказы видны в списке, но считаются ненадёжным пополнением.

Потребность после прихода округляется вверх до упаковки с учётом минимального количества упаковок. Например, при остатке 25, темпе 20, сроке поставки один день и покрытии пять дней к приходу останется 5 единиц. Цель — 100 единиц. Потребность 95 единиц округляется до 100 при упаковке 10. Если подходящее окно заказа сегодня и действует прайс, поле `draft` содержит тело для `PUT /orders/{id}`. Передавайте тело целиком, включая `replenishment` с параметрами и, для сохранённого расчёта, `policyVersion`. Такие черновики содержат один артикул и хранят параметры расчёта в своей версии. Для заказа с произвольным объёмом создайте ручной черновик без поля `replenishment`.

При сохранении и при отдельном утверждении сервер пересчитывает потребность на согласованном снимке базы и сверяет дату поставки, версию цены и число упаковок. Если изменились параметры сохранённого правила, API возвращает `409 replenishment_policy_changed`. Если изменилось предложение, возвращает `409 purchase_replenishment_changed`. При обновлении прайса на утверждении возможен `409 supplier_price_changed`. В ответ на конфликт получите свежую рекомендацию. Если она содержит черновик, сохраните его в том же заказе с актуальным `expectedRevision` и отдельно подтвердите новую версию. При потере ответа повторите исходную команду с тем же идентификатором и версией. Проверка черновика всегда использует данные на момент нового расчёта.

Фоновый обработчик запускается вместе с API. Он считает рекомендации для артикулов с сохранёнными настройками после местной полуночи, при достижении времени окончания приёма заказов, после обновления настроек и при изменении входных данных. Продажи, приёмка, списания, смена срока партии и изменения по ожидаемым поставкам оставляют события в PostgreSQL в той же транзакции. Обработчик объединяет события по товару и фиксирует результат вместе с удалением обработанных событий. Работа продолжится после перезапуска API. Интервал опроса `Purchasing__ReplenishmentRefreshSeconds` по умолчанию 10 секунд, допустимые значения от 1 до 300.

В ответе `/snapshot` статус `pending` означает ожидание первого результата, `ready` — готовый результат, `stale` — ожидание обновления, `unavailable` — расчёт сейчас невозможен, например поставщик отключён. Для `stale` API может вернуть прошлый расчёт без тела черновика. Сравнивайте `policyVersion` и `calculatedPolicyVersion`, показывайте `calculatedAt`. Если нужен результат сразу после операции, используйте синхронный маршрут без `/snapshot`.

## Закупочная стоимость прихода

`GET /costs` и `PUT /costs` с префиксом накладной доступны админу. Админ указывает `expectedVersion` и все строки `items`, у каждой `productId`, `lotId`, `unitPrice` и необязательные суммы `discount`, `includedTax`, `allocatedCharges`. Последние три поля относятся ко всей строке, админ вводит уже согласованные суммы. Сервер округляет произведение фактического количества и цены до 0,01 сума, вычитает скидку и добавляет налог и расходы. При проверке стоимости увеличивается версия документа. Для проведения передайте версию из `receiptVersion`.

После исправления накладной ранее введённая стоимость получает статус `stale` и требует повторной проверки. При проведении стоимость каждой партии сохраняется со складским движением в той же транзакции. По умолчанию приход может быть проведён без стоимости для совместимости со старыми клиентами. `Purchasing__RequireReceiptCosts=true` требует сверенные суммы для проведения.

## Себестоимость и оценка остатков

`GET /v1/reports/stores/{storeId}/stock-valuation` доступен админу назначенной точки с MFA. Передайте `productId` для фильтра по товару. `items` содержит до 50 непустых партий с количеством и стоимостью обычного остатка и карантина. Передайте `nextOffset` как `offset` для следующей страницы. Итоги относятся ко всем партиям в фильтре. `knownValue` суммирует оценённые остатки. Если `unvaluedLotCount` больше нуля, полный итог `totalValue` равен `null`.

`GET /v1/reports/stores/{storeId}/stock-valuation/csv` выгружает оценку по тому же фильтру `productId`. Файл содержит партии, итог, часовой пояс и время расчёта. Неизвестные суммы оставляются пустыми. Максимум для одной выгрузки составляет 1000 непустых партий. При превышении API возвращает `409 stock_valuation_export_limit`. Укажите товар, чтобы сузить выборку. Успешная выгрузка фиксируется в аудите.

`POST /v1/reports/stores/{storeId}/stock-valuation/snapshots` с `operationId` сохраняет количество в продаже и карантине и текущую учётную стоимость каждой непустой партии. Неизвестная стоимость сохраняется как `null`. Администратор магазина с MFA делает снимок вручную. Сервер сохраняет местную дату магазина, часовой пояс и точное время. Повтор с тем же `operationId` возвращает сохранённый снимок. Новый идентификатор в ту же местную дату получает `409 stock_snapshot_date_exists`.

`GET /v1/reports/stores/{storeId}/stock-valuation/snapshots?date=YYYY-MM-DD` читает ранее сделанный снимок. Поддерживаются `productId` и `offset`, размер страницы до 50 строк. Если снимка за эту дату нет, API возвращает `404 stock_snapshot_not_found`.

Метод пилота `movingWeightedAverageByLot` использует текущую стоимость партии и общее количество в обоих складских остатках. Приход добавляет согласованную закупочную стоимость, включая скидки поставщика и согласованные расходы. При продаже, списании и возврате поставщику стоимость уменьшается пропорционально выбывшему количеству. Сумма зачёта поставщика отдельно рассчитывается по исходной накладной. Розничная скидка меняет выручку. Возврат покупателя восстанавливает себестоимость исходной продажи. Частичные возвраты округляются накопительно, чтобы полный возврат восстановил всю исходную сумму. Перевод в карантин сохраняет общую стоимость. Излишек при инвентаризации оценивается по текущей средней стоимости партии, если она известна. Округление выполняется до 0,01 в момент движения, при полном выбытии снимается вся оставшаяся стоимость.

Поздний документ влияет на стоимость в момент проведения. Оценка уже проведённых движений сохраняется в истории. Приход без цены делает стоимость непустой партии неизвестной. Оценка снова появляется при первом полностью оценённом поступлении в пустую партию. Миграция заполняет стоимость старого остатка, если количество полностью сверяется с оценёнными приходами и начальным вводом и с тех пор по партии не было продаж, возвратов или движений, изменивших общее количество. Исторические списания и продажи без исходной оценки остаются без себестоимости.

На существующей базе перед `018_inventory_cost.sql` остановите все экземпляры API и сохраните резервную копию. Запускайте новую версию после миграции. Совместная работа со старым API нарушит согласованность количества и стоимости, поскольку старая версия обновляет только количество. Для отката после начала новых проводок сверяйте движения, появившиеся после резервной копии.

## Остатки сроки годности и списания

| Маршрут | Действие |
| --- | --- |
| `GET /v1/expiry/cashier` | Кассир видит сроки только своей точки. |
| `POST /v1/expiry/cashier/shelf-tasks` | Пометка о снятии с полки по полям `taskId`, `productId`, `lotId`, `quantity`. |
| `GET /v1/stores/{storeId}/stock/expiry` | Сроки по партиям назначенной точки для админа. |
| `GET /v1/stores/{storeId}/stock/lots` | Остатки и ревизии партий для админа. Поддерживает `productId` и `offset`. |

Сроки считаются по местному дню точки. Фильтр `filter` принимает `today`, `within3`, `within7`, `expired`, `missing` и `all`. Последний включает партии с датой и партии без обязательной даты. Обе выборки сроков поддерживают `offset`. Ответ поиска по штрихкоду включает `requiresLotVerification`. При наличии проблемной партии кассир сверяет упаковку и передаёт допустимый `lotId`. Просроченные партии и партии без обязательной даты сервер отклоняет при продаже.

Пометка о снятии с полки и её закрытие ведутся отдельно от складских движений. Для движения админ отправляет `operationId`, `productId`, `lotId`, `kind`, `quantity` и `reason`. Действие `quarantine` переводит количество в карантин. `writeOffStock` и `writeOffQuarantine` списывают из соответствующего остатка. Учётный остаток включает карантин. Доступный остаток учитывает срок и статус партии. Повтор того же движения с прежним ID возвращает записанный результат.

## Начальные остатки

Маршруты имеют префикс `/v1/stores/{storeId}/stock/opening-balances` и доступны админу назначенной точки с MFA.

| Метод и маршрут | Действие |
| --- | --- |
| `POST /preview` | Проверить импорт и увидеть сверку. Поле `postedAt` пустое до проведения. |
| `POST /` | Провести импорт. Партии, движения, сверка и аудит записываются одной транзакцией. |
| `GET /{id}` | Получить сохранённую сверку по `operationId`. |
| `GET /{id}/csv` | Скачать сверку в CSV UTF-8. Выгрузка отражается в аудите. |

Для предпросмотра и проведения отправьте `operationId`, `sourceReference` (название файла или идентификатор источника), `reason` и один из вариантов `items` или `csv`. В `items` передаются `productId`, `lotId`, `expiryDate`, `stockQuantity`, `quarantineQuantity` и `totalCost`. Для импорта CSV передайте содержимое файла в строке с заголовком `productId,lotId,expiryDate,stockQuantity,quarantineQuantity,totalCost`. Используйте запятую как разделитель, точку в дробях и дату `yyyy-MM-dd`. Для срока и стоимости допустимы пустые значения. Поле `row` в ошибке указывает номер строки данных, для CSV первая строка отведена заголовку.

За раз можно провести до 100 партий. Все партии одного товара в точке вносятся одним документом до первой приёмки или другого создания партии. Для штучного товара количество целое. Просроченные партии и партии без обязательного срока допускаются только в карантин. Дата сверки берётся по часовому поясу точки в момент проведения. `totalCost` хранит общую исходную стоимость строки, включая карантин. `knownCost` суммирует заполненные значения, а `unpricedLineCount` показывает количество строк без цены. Поступление отражается в отчёте движений как `kind=opening`.

После тайм-аута повторите тот же запрос с тем же `operationId`. Если документ уже проведён, API вернёт сохранённую сверку. Изменение данных под тем же идентификатором или попытка ввести остаток товара, у которого уже есть партии, вернёт `409`.

## Инвентаризация

Маршруты имеют префикс `/v1/stores/{storeId}/stock/inventories` и доступны админу.

| Метод и маршрут | Действие |
| --- | --- |
| `POST /` | Открыть пересчёт по `inventoryId` и `reason`. Для выборочного пересчёта передайте `lots` до 100 пар `productId` и `lotId`. Для пересчёта по области передайте `scope` вместо `lots`. |
| `GET /` | Список документов с фильтром `status` и смещением `offset`. |
| `GET /{id}` | Прочитать документ. `blind=true` скрывает учётные и ранее введённые количества. |
| `POST /{id}/count` | Внести фактические количества с `expectedVersion` и списком `items`. Для каждой партии передаются `productId`, `lotId`, `lotRevision`, `stockQuantity` и `quarantineQuantity`. Для выборочного документа передайте весь список. Для пересчёта по области можно отправлять порции до 100 партий. |
| `POST /{id}/refresh` | Добавить в незакрытый документ по области новые подходящие партии. Уже сохранённые подсчёты остаются в документе. Тело запроса не требуется. |
| `POST /{id}/post` | Утвердить документ, передав `expectedVersion` после пересчёта. Корректировки и аудит фиксируются одной транзакцией. |

Для полного пересчёта передайте `scope: {"kind":"full"}`. Для категории используйте `{"kind":"category","category":"Молочные продукты"}` с точным названием из каталога. Для одного товара используйте `{"kind":"product","productId":"…"}`. В область входят известные учёту партии магазина, включая нулевые остатки и карантин. Документ сохраняет список, выбранный при создании. Если после этого товар сменил категорию, уже включённые партии остаются в документе. Новые подходящие партии обнаруживаются перед проведением. При `409 inventory_scope_changed` вызовите `/refresh` и пересчитайте добавленные партии. Документ остаётся в статусе `draft`, пока для всех партий не сохранён результат.

Перед физическим пересчётом клиент получает актуальные ревизии через `GET /{id}?blind=true`. Для пересчёта по области поле `countStatus` показывает, требуется ли первый подсчёт (`pending`), нужен ли повторный (`stale`) или результат соответствует текущей ревизии (`counted`). При изменении партии до сохранения или проведения сервер возвращает `409 inventory_lot_changed` и откатывает запрос целиком. Продажи, возвраты и приёмки продолжают работать между этапами. При проведении учитываются только найденные расхождения. В обычной карточке `inventoryCostDelta` показывает известную стоимость расхождения по актуальной ревизии. В проведённой карточке поле показывает сумму из журнала.

При потере ответа на создание повторите запрос с тем же `inventoryId` и теми же параметрами. Для подсчёта повтор той же последней порции с исходным `expectedVersion` возвращает документ, если после неё документ не менялся. После проведения повтор запроса с версией, которую проводили, возвращает проведённый документ. При конфликте версии прочитайте текущую карточку перед продолжением.

## Каталог и цены

| Метод и маршрут | Действие |
| --- | --- |
| `GET /v1/catalog/search?q=...` | Кассир ищет активный товар своей точки по имени, артикулу или точному штрихкоду. |
| `GET /v1/catalog/products/{id}` | Кассир открывает товар после ручного поиска и видит годные партии. |
| `GET /v1/catalog/barcodes/{barcode}` | Поиск по одному из кодов товара. `quantityFactor` показывает число базовых единиц в упаковке. |
| `GET /v1/stores/{storeId}/catalog/products` | Список админа с `q`, `offset` и `includeArchived`. |
| `GET` и `PUT /v1/stores/{storeId}/catalog/products/{id}` | Чтение и запись карточки. При создании `expectedVersion=0`, при обновлении — текущая версия. |
| `PUT /v1/stores/{storeId}/catalog/products/{id}/price` | Записать цену точки по `expectedVersion`, `unitPrice`, `active` и `reason`. |
| `GET /v1/stores/{storeId}/catalog/products/{id}/price-history` | История версий цены с датой, причиной и автором. |

Карточка содержит `name`, `unit` (`piece` или `kg`), `requiresExpiry`, `sku`, `category`, `brand`, `supplierRef`, `taxProfile` и массив `barcodes` со строками `code` и `quantityFactor`. Пустой массив разрешён для ручного поиска. Первый код считается основным. Артикулы и штрихкоды уникальны в организации. Для изменения общей карточки админ должен иметь доступ ко всем её точкам. Базовая единица фиксируется при создании. Клиент пересчитывает упаковки в базовое количество до отправки продажи или прихода.

Карточка создаётся без розничной цены. При продаже сервер проверяет наличие цены и её версию. Архивирование через `active=false` скрывает товар из продажи на точке. Старые чеки, цены и ранее созданные приходы доступны. Миграция переносит старые числовые штрихкоды и текущие цены. История цен до миграции неизвестна, поэтому первая запись для старой карточки помечается `migration_baseline`.

### Предложения приёмщика

`POST /v1/stores/{storeId}/receiving/catalog/proposals` принимает `proposalId` и объект `product` с названием, единицей, признаком срока, артикулом, категорией и штрихкодами. Приёмщик видит свои предложения через `GET` на том же маршруте. Админ видит очередь своей точки и вызывает `POST /v1/stores/{storeId}/catalog/proposals/{id}/approve` или `/reject`. Тело содержит `reason`, обязательную при отказе. Одобрение создаёт карточку без цены.

### Импорт CSV

`POST /v1/stores/{storeId}/catalog/import` принимает JSON с полями `preview` и `csv`. Для начала отправьте `preview=true`. Для подтверждения повторите тот же CSV с `preview=false`. Пакет сохраняется одной транзакцией. При конфликте ответ указывает номер строки `row`, а изменения пакета откатываются.

```csv
productId,expectedVersion,name,unit,requiresExpiry,sku,category,brand,supplierRef,taxProfile,barcodes,unitPrice,expectedPriceVersion
00000000-0000-0000-0000-000000000901,0,"Молоко, 1 л",piece,false,MILK-01,Молоко,,,,000910;000911*6,2000.25,1
```

До 100 строк и 48 000 символов CSV в одном запросе с общим лимитом JSON 64 КиБ. Ключ обновления — `productId`. Поля карточки заменяются полностью, пустые необязательные ячейки очищают значения. Штрихкоды разделяются точкой с запятой, коэффициент упаковки указывается после звёздочки. Пустые поля `unitPrice` и `expectedPriceVersion` сохраняют текущую цену. Импорт цены сохраняет признак архивации. Допускается UTF-8 с BOM. Числа используют десятичную точку, штрихкоды читаются как строки. Файл XLSX для этого маршрута можно сохранить из Excel в CSV.

## Операции кассовой смены

Маршруты кассира используют JWT и ключ зарегистрированной кассы. Маршруты админа ограничены назначенной точкой.

| Метод и маршрут | Действие |
| --- | --- |
| `POST /v1/shifts/{shiftId}/cash-movements` | Записать внесение или изъятие. Поля `operationId`, `direction` (`in` или `out`), `amount`, `reason`. |
| `GET /v1/shifts/{shiftId}/cash-movements` | Список движений своей смены. |
| `GET /v1/stores/{storeId}/registers/{registerId}/shifts/{shiftId}/cash-movements` | Список движений для админа. |

Изъятие сверх ожидаемой суммы отклоняется. При закрытии смены сервер складывает размен, наличные продажи и внесения, затем вычитает наличные возвраты и изъятия. Поля `cashIn` и `cashOut` видны в отчёте админа и итогах закрытой смены кассира. Повтор движения с прежним ID и телом возвращает записанную операцию.

## Отложенные корзины

| Метод и маршрут | Действие |
| --- | --- |
| `PUT /v1/shifts/{shiftId}/carts/{id}` | Отложить корзину с `expectedVersion=0` или обновить её по текущей версии. `items` имеют формат строк продажи. |
| `GET /v1/shifts/{shiftId}/carts` | Активные корзины своей смены. `includeInactive=true` включает отменённые, проданные и истёкшие. |
| `GET /v1/shifts/{shiftId}/carts/{id}` | Корзина и проверка строк по текущей цене, доступности и остатку. |

Отложенная корзина действует четыре часа. Товар остаётся доступен для продажи. При проведении продажи передайте `cartId` и `cartVersion`. После проверки цены касса отправляет актуальные `priceVersion`. Если меняются партии или количество, сначала обновите корзину. Сервер закрывает её вместе с успешной продажей. Пока есть активные отложенные корзины, закрытие смены возвращает `shift_has_parked_carts`.

## Скидка на чек и поиск чеков

Ручная скидка передаётся в `POST /v1/sales` как `discount: { kind, value, reason }`. Допустимы `amount` и `percent`. По умолчанию ручные скидки отключены. `Sales__MaxManualDiscountPercent` включает их и задаёт максимальный процент от чека. Сервер распределяет скидку по строкам пропорционально стоимости и сохраняет итог каждой строки. Возвраты рассчитываются по сохранённым суммам. Автоматические акции, скидки на отдельную позицию и правила совмещения скидок входят в отдельный этап.

`GET /v1/sales/history` возвращает продажи кассира на его кассе. `GET /v1/stores/{storeId}/sales/history` возвращает продажи назначенной точки админу. Общие фильтры — `receiptId`, `shiftId`, `date`, `amount` и `offset`. Админу также доступны `registerId` и `cashierId`. Дата относится к часовому поясу точки. Карточка чека доступна через `GET /v1/sales/{id}` кассиру и `GET /v1/stores/{storeId}/sales/{registerId}/{id}` админу.

## Отчёт по продажам за период

Маршруты доступны админу назначенной точки. Укажите даты `from` и `to` в формате `YYYY-MM-DD`. Обе даты входят в отчёт. Максимальный период — 93 календарных дня. Дополнительные фильтры `registerId` и `cashierId` можно использовать вместе. Касса и сотрудник должны относиться к выбранной точке. В отчёт входят и дни без операций.

| Метод и маршрут | Результат |
| --- | --- |
| `GET /v1/reports/stores/{storeId}/sales` | Сводка `total`, разбивка `days`, применённые фильтры, часовой пояс магазина и время расчёта. |
| `GET /v1/reports/stores/{storeId}/sales/csv` | Та же сводка в CSV с дневными строками и строкой `total`. Выгрузка проверяет текущие права и записывает фильтры и автора в аудит. |

Отчёт берёт только записанные сервером продажи, возвраты и движения денег. День определяется по часовому поясу магазина. Продажа попадает в день оформления чека. Возврат относится к дате, кассе и сотруднику, оформившим возврат. Поэтому чистая выручка отдельного дня может быть отрицательной. Стартовый размен и остаток в ящике относятся к сводке смены.

`grossSales` — сумма до скидок, `sales` — продажи после скидок, `netSales` — продажи после скидок за вычетом возвратов. `averageCheck` делит `sales` на количество чеков продажи и округляется до 0,01. При отсутствии продаж он равен `null`. Наличные и ручной безнал показаны отдельно. Внесения и изъятия `cashIn` и `cashOut` относятся к движению денег и не входят в выручку.

CSV содержит до 94 строк данных и возвращается сразу. Разделитель — запятая, числа используют точку, кодировка UTF-8 с BOM. За чеками за отдельный день можно обращаться к существующему маршруту `GET /v1/stores/{storeId}/sales/history?date=YYYY-MM-DD` с теми же фильтрами кассы и кассира.

## Отчёт о валовой прибыли

`GET /v1/reports/stores/{storeId}/profit?from=YYYY-MM-DD&to=YYYY-MM-DD` возвращает итоги по выбранному магазину и каждому дню периода. Обе даты включаются, максимальная длина периода составляет 93 календарных дня. Дни рассчитываются в часовом поясе магазина. Доступ имеет администратор назначенного магазина с MFA. Маршрут `/profit/csv` с теми же фильтрами выгружает данные в CSV UTF-8 и записывает автора и период в аудит.

Чистая выручка `netRevenue` равна сумме продаж после скидок за вычетом возвратов. Себестоимость продаж `costOfGoodsSold` равна сохранённой себестоимости продаж за вычетом восстановленной стоимости возвратов. Возврат относится к дате его оформления. Валовая прибыль `grossProfit` равна разнице между чистой выручкой и себестоимостью продаж. `grossMarginPercent` делит валовую прибыль на чистую выручку и возвращает процент с округлением до 0,01. Процент рассчитывается при положительной чистой выручке. Итоговый процент рассчитывается из итоговых сумм периода.

При отсутствии себестоимости хотя бы у одной строки продажи или возврата показатели `costOfGoodsSold`, `grossProfit` и `grossMarginPercent` равны `null`. Отчёт показывает известные суммы себестоимости и количество строк без оценки. В CSV неизвестные значения остаются пустыми.

Складские расходы `inventoryExpenses` включают стоимость проведённых списаний и недостач и показываются отдельно от валовой прибыли. Суммы по списаниям и недостачам видны раздельно. При отсутствии оценки хотя бы одного расхода полный итог складских расходов равен `null`, а известные суммы и число строк без оценки остаются доступны. Учёт аренды и прочих операционных расходов запланирован отдельно.

## Журнал складских движений

Администратор назначенной точки с MFA может получить отчёт по срокам годности через `GET /v1/reports/stores/{storeId}/stock-expiry`. Фильтры `today`, `within3`, `within7`, `expired`, `missing` и `all` используют местный день магазина. По умолчанию применяется `within7`. В отчёт входят непустые партии с датой либо обязательным сроком. В строке указаны срок, число дней, количество в обычном остатке и карантине и общая учётная стоимость партии. Для следующей страницы передайте `nextOffset` как `offset`.

`GET /v1/reports/stores/{storeId}/stock-expiry/csv` выгружает партии по тому же фильтру и записывает успешную выгрузку в аудит. При превышении 1000 строк сервер возвращает `409 stock_expiry_export_limit`. Неизвестная стоимость остаётся пустой в CSV.

Отдельный отчёт `GET /v1/reports/stores/{storeId}/stock-losses` показывает проведённые списания из обычного остатка и карантина, а также строки инвентаризации с чистым выбытием. Передайте `from` и `to` в формате `YYYY-MM-DD` и при необходимости `productId`. Обе даты включаются, период ограничен 93 календарными днями по часовому поясу магазина. В каждой строке указаны тип операции, документ, партия, причина из документа, количество выбытия и его стоимость. При неизвестной стоимости JSON содержит `null`. Для продолжения передайте `nextCursor` как `after` с теми же фильтрами.

Маршрут `/stock-losses/csv` принимает те же фильтры периода и товара. Неизвестная стоимость остаётся пустой. При числе строк больше 1000 API возвращает `409 stock_loss_export_limit`. Доступ к отчёту и выгрузке есть у администратора назначенной точки с MFA. Успешная выгрузка записывается в аудит.

| Метод и маршрут | Результат |
| --- | --- |
| `GET /v1/reports/stores/{storeId}/stock-movements` | Строки по товарам и партиям, применённые фильтры, время запроса и курсор следующей страницы. |
| `GET /v1/reports/stores/{storeId}/stock-movements/csv` | CSV с теми же фильтрами. Сервер повторно проверяет доступ и записывает успешную выгрузку в аудит. |
| `POST /v1/reports/stores/{storeId}/stock-movements/exports` | Принимает фоновую CSV-выгрузку и возвращает `202` со ссылкой на статус в заголовке `Location`. |
| `GET /v1/reports/stores/{storeId}/stock-movements/exports/{id}` | Возвращает состояние задания. |
| `GET /v1/reports/stores/{storeId}/stock-movements/exports/{id}/file` | Отдаёт готовый CSV автору с действующим назначением и MFA. |

Отчёт доступен админу назначенной точки с MFA. Передайте `from` и `to` в формате `YYYY-MM-DD`. Обе даты включаются, максимальный период — 93 календарных дня. Можно передать `productId`, а вместе с ним `lotId`. Фильтр `kind` принимает `receipt`, `sale`, `customerRefund`, `quarantine`, `inventory`, `writeOffStock`, `writeOffQuarantine`, `supplierReturn`, `opening`. Значение `writeOff` включает оба типа списания.

В JSON `limit` задаёт размер страницы от 1 до 100, по умолчанию 50. Передайте полученный `nextCursor` как `after` с теми же фильтрами. Порядок идёт от новых движений к старым и учитывает идентификаторы строк с одинаковым временем. Синхронный CSV выгружает до 1000 строк одним файлом. При `409 stock_movement_export_limit` доступна фоновая выгрузка с теми же фильтрами.

Для фоновой выгрузки передайте фильтры в JSON вместе с клиентским UUID `operationId`. При потере ответа отправьте то же тело повторно. Сервер вернёт `202` и текущее состояние того же задания. Изменённые фильтры с тем же ID дают `409 stock_movement_export_operation_conflict`. Считывайте статус по `Location` раз в несколько секунд. Состояние `queued` означает ожидание или выполнение, `ready` разрешает скачивание, `failed` содержит `errorCode`, `expired` означает, что срок скачивания истёк. Скачивание до готовности возвращает `409`, после истечения срока — `410`. При отзыве назначения автор теряет доступ к статусу и файлу.

Один файл содержит до 10 000 строк и до 8 МиБ. Слишком большой отчёт завершает задание с `stock_movement_background_export_limit`. На магазин одновременно допускается до 10 ожидающих и готовых заданий с действующими файлами. При заполнении сервер возвращает `409 stock_movement_export_capacity`. Файл хранится 24 часа после подготовки, затем обработчик очищает содержимое. Задание сохраняется в PostgreSQL, поэтому обработчик продолжает работу после перезапуска API. В аудит попадают постановка, результат и успешное скачивание.

В каждой строке отдельно показаны изменение обычного остатка (`stockDelta`), карантина (`quarantineDelta`) и суммарного остатка (`totalDelta`). При переводе в карантин суммарное изменение равно нулю. Отчёт включает только проведённые операции. Местная дата определяется в часовом поясе точки. По `documentId`, `registerId` и, где применимо, `sourceDocumentId` и `sourceRegisterId` можно сопоставить строку с исходными документами. Для списаний и корректировок выводится записанная причина.

Закупочная стоимость проведённой строки прихода передаётся в `receivingCost`, а сумма зачёта поставщика — в `supplierCredit`. Поле равно `null`, если сумма неизвестна или показатель неприменим. Для начальных остатков известная исходная стоимость доступна в `openingCost` в JSON и в отдельной CSV-сверке. Поле `inventoryCostDelta` в JSON показывает изменение стоимости остатков по проведённому движению. Отрицательное значение соответствует выбытию. Если сумма неизвестна, поле отсутствует. Это же поле доступно в карточках складских операций. Общая CSV-выгрузка движений сохраняет прежний набор колонок.

## Серверные исключения

Отчёт `GET /v1/reports/stores/{storeId}/exceptions` доступен администратору назначенной точки с MFA. Допустимые фильтры `code` включают `missingRequiredExpiry` для непустых партий без обязательной даты, `invoiceScanPending` и `invoiceScanRejected` для вложений открытых приёмок, `cashDifference` для закрытых смен с ненулевым расхождением. Строка содержит ID объекта и связанные идентификаторы для перехода к карточке. Для следующей страницы передайте `nextOffset` как `offset`. Размер страницы задаёт `limit` от 1 до 100.

Кассир отправляет событие через `POST /v1/register/diagnostics` с токеном, ID и ключом кассы. В JSON передайте `eventId`, `shiftId`, `code` и `operationId`. Доступны `saleOutcomeUnknown` для потерянного ответа на продажу, `printFailed` для ошибки печати сохранённой продажи этой смены и `syncFailed` для ошибки синхронизации. У `syncFailed` идентификатор операции необязателен. Допускается доставка после закрытия своей смены. Точный повтор возвращает сохранённое событие, изменённые данные с тем же `eventId` дают `409 register_diagnostic_event_conflict`. Ответ содержит серверное время приёма `receivedAt`.

Эти коды доступны и в отчёте админа. У диагностических строк `objectId` равен `eventId`, также передаются `registerId`, `shiftId` и переданный клиентом `operationId`. Ошибки печати и синхронизации остаются в истории. `saleOutcomeUnknown` отображается, пока у сервера нет продажи с таким ID в той же смене, на той же кассе и у того же кассира. При потере ответа касса сверяет продажу через `GET /v1/sales/{id}` и при необходимости повторяет исходное тело с тем же `operationId`.

## Настройки HTTPS и учётных записей

Вне Development API принимает только HTTPS. Настройте TLS-сертификат Kestrel, HTTPS-адрес доверенного OIDC-провайдера в `Auth__Authority`, аудиторию в `Auth__Audience` и значение `acr` для входа админа с WebAuthn в `Auth__AdminAcr`. Сервер проверяет действующие роли и назначения в PostgreSQL при каждом запросе. Для подключения Windows-клиента потребуется настроить выдачу токенов у провайдера и регистрацию устройств. Стендовые HMAC-токены включаются только в Development.

Храните пароль БД, ключи устройств и сертификат отдельно от исходников. Кассовый ПК обращается только к HTTPS API. PostgreSQL доступен только приложению и администрированию через закрытую сеть. Таблица аудита позволяет сервисной учётной записи только добавлять события.

### Регистрация и отзыв кассы

Администратор назначенного магазина с MFA управляет устройствами через `/v1/stores/{storeId}/registers`. Для стенда создайте ключ криптографическим генератором, например `openssl rand -hex 32`. Передайте его только по HTTPS и сохраните на устройстве в защищённом хранилище. В базе хранится SHA-256 ключа, в ответах и аудите ключ отсутствует.

| Метод и маршрут | Действие |
| --- | --- |
| `GET /registers` и `GET /registers/{id}` | Список и карточка с версией, статусом и назначенными кассирами. |
| `POST /registers` | Передайте новый `registerId`, `name`, `cashierId` активного кассира точки и `registerKey`. Повтор того же запроса до изменения устройства возвращает ту же карточку. |
| `POST /registers/{id}/rotate-key` | Передайте текущий `expectedVersion` и новый `registerKey`. После фиксации старый ключ перестаёт действовать. |
| `POST /registers/{id}/revoke` | Передайте текущий `expectedVersion`. Кассовые запросы от устройства блокируются, история смен и чеков остаётся доступна администратору. |

Повтор последней ротации или отзыва с исходной версией возвращает карточку результата. При конфликте прочитайте свежую карточку перед новой операцией. При плановом отзыве сначала закройте смену. Экстренный отзыв блокирует устройство сразу, открытая смена остаётся в учёте без автоматического закрытия.

### Доступ сотрудников

Администратор с MFA использует `GET /v1/stores/{storeId}/staff` для списка назначений своего магазина. Для подключения вызовите `POST` по тому же пути с точным `subject` учётной записи настроенного провайдера и ролью `cashier`, `receiver` или `admin`. Для кассира укажите `registerId` активной кассы магазина. Провайдер создаёт аккаунты и выдаёт токены. Повтор запроса с тем же назначением безопасен. Роль существующей учётной записи фиксирована.

Для отзыва вызовите `POST /v1/stores/{storeId}/staff/{id}/revoke`. Доступ прекращается в выбранной точке при следующем запросе. Назначения в других магазинах и исторические операции сохраняются. Повтор подключения ранее отозванного назначения возвращает `409 staff_access_revoked`. Администратор сохраняет своё назначение.

Перед применением миграции `020_staff_store_access.sql` остановите прежние экземпляры API. Только новая версия учитывает локальный отзыв при проверке доступа.

### Журнал действий магазина

`GET /v1/stores/{storeId}/audit` доступен действующему администратору назначенной точки с MFA. Укажите `from` и `to` в формате `YYYY-MM-DD` для периода до 93 дней включительно по часовому поясу магазина. Параметр `action` отбирает точное имя события. Каждая запись содержит дату, действие, ID сотрудника, объекта и кассы при наличии, а также ID запроса. Следующая страница запрашивается с `after=nextCursor` и теми же фильтрами. Размер страницы задаёт `limit` от 1 до 100, по умолчанию 50.
