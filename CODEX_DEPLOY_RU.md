# Выпуск серверного исправления «Касса»

База изменений — архив `Kassa_Server_2026-11-17_ee9b56b.zip`. Рабочее окружение при подготовке архива не использовалось.

## Изменения

- Проверка операторской сессии и продление её срока активности используют одно соединение и транзакцию PostgreSQL. При пуле из одного соединения исходный API возвращал `503 database_temporarily_unavailable`. Исправленная версия прошла объединённую проверку входа и кассовых операций при таком же размере пула.
- Запрос `GET /v1/me/roles?storeId=…` с операторской сессией проверяет, что магазин совпадает с магазином сессии. Запрос к другому магазину получает `409 operator_store_mismatch`, даже если владелец имеет доступ к обоим магазинам. Переключение магазина проходит через новую операторскую сессию.
- Проверка остатка наличных при возврате и маршруты входа операторов уже входят в базовую версию. Windows 0.8.5 восстанавливает смену через `GET /v1/shifts/active`.

## Развёртывание на действующем сервере

1. Определите исходный коммит текущего API и проверьте схему PostgreSQL. Если на сервере есть изменения поверх `ee9b56b`, перенесите два изменения из `src/Kasa.Api/Access.cs` и `src/Kasa.Api/Program.cs` в текущую ветку и соберите её. Сохраните текущий образ или опубликованный комплект для отката.
2. Сделайте резервную копию базы и проверьте её восстановление в отдельном экземпляре. Если схема уже включает `db/038_store_operator_auth.sql`, для данного исправления SQL применять не требуется. Для более старой схемы примените отсутствующие миграции по шагам перехода в `docs/STORE_OPERATOR_AUTH.md` на восстановленной копии, затем на рабочей базе. Скрипты в `/docker-entrypoint-initdb.d` выполняются при инициализации пустого тома.
3. Соберите API с .NET 10. Используйте том PostgreSQL, конфигурацию Keycloak, сетевые параметры и секреты действующего развёртывания. Сохраните текущее значение `KASA_REQUIRE_OPERATOR_SESSION`. Для развёртывания совместимого API со старыми клиентами выставьте `false`, если операторские сессии ранее не были обязательными. Клиент 0.8.5 передаёт операторскую сессию и при `false`.
4. Сначала проверьте сборку и данные в тестовой точке. На действующем сервере обновите сервис API по существующей процедуре выпуска. Для шаблона `deploy/compose.production.yaml` предварительно опубликуйте `Kasa.Api.csproj` в `.deploy/publish` с параметром `/p:UseAppHost=false`. После публикации Compose может пересобрать только сервис `api` командой `up -d --no-deps --build api` с тем же файлом Compose, именем проекта и защищённым env-файлом.
5. Проверьте `GET /health/live`, вход через Keycloak, список магазинов, вход оператора, назначение кассы, открытие смены, поиск по штрихкоду, продажу и списание на тестовых данных. Проверьте восстановление по исходному `operationId`, отказ возврата при недостатке денег и вход старым клиентом, если он используется.
6. При регрессии верните предыдущий образ API. Эти исправления не меняют схему базы.

Сборка с `-warnaserror` и три теста .NET прошли. На изолированных .NET 10 и PostgreSQL 17 прошёл сценарий входа владельца и сотрудника, назначения кассы, открытия смены, поиска товара, продажи, повторной отправки, списания с 10 до 9 и закрытия смены. Пройдены проверки отзыва сессий, границы магазина и режима без обязательной операторской сессии. Также прошёл штатный сценарий `tests/run.sh` на локальном PostgreSQL 17, включая проверку отказа наличного возврата при недостатке средств и гонки с изъятием наличных.

Архив содержит серверные исходники. Обработка быстрых сканов, офлайн-кэш и интерфейс сверки офлайн-очереди находятся в Windows-клиенте. Проверка физического сканера и реального входа через Keycloak выполняется на стенде выпуска.
